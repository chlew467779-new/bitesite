# Merchant password authentication and self-registration

This package adds password sign in, self-registration, password recovery and private restaurant creation. CH decided on 2026-09-29 to remove Magic Link sign-in because email sending is limited; Batch 7 removed its login UI. Existing accounts use Forgot password to set a password. There is no Admin invitation requirement for creating a new draft.

Account login and restaurant authorization stay separate. Every restaurant route still resolves active Owner membership. `POST /api/merchant/restaurants` accepts only a name and a retry request ID. The server verifies the bearer user and supplies its identity to a service-only transaction. The transaction rechecks email confirmation and creates a managed hidden draft, Owner membership and audit record together. The account email is never copied to the restaurant's public contact email. Slugs are generated by the server; clients cannot claim existing restaurants. Retried requests return the same draft; suspended/transferred ownership cannot be restored by replay.

## Local verification

`npm run test:merchant-auth` executes input validation and the real route handlers with mocked provider I/O. `supabase/tests/merchant_password_onboarding.sql` executes cooldown, grants, ownership, privacy, retry and forced rollback checks against Postgres in a rolled-back transaction. Existing merchant access tests cover foreign-restaurant authorization.

## Environment prerequisites

Apply `20260927090355_merchant_password_onboarding.sql` after the D1a state foundation. Configure Supabase Email provider to allow self-signup, require email confirmation, and enforce minimum password length 8. Do not enable required character mixtures. No leaked-password protection is assumed. Confirm SMTP configuration and allow the site's exact `/merchant` and `/merchant/reset-password` redirect URLs. Existing accounts that previously used Magic Link can set their first password using Forgot password or the authenticated password page. Auth settings and redirect URLs are required before registration/recovery can work in the target environment; they are not changed by this code package.

## Cooldown boundary

The website's password route counts consecutive invalid credentials by the current source IP. Five failures start a 15-minute cooldown; success clears the count. The database serializes attempts with a 30-second ticket, rejects reused/foreign tickets and prevents delayed responses from modifying a newer attempt. Provider failures do not count as wrong passwords. Password reset remains available during cooldown; changing a password does not shorten the source cooldown. A shared network shares its source counter, while other sources and public listings are unaffected. Vercel's `x-vercel-forwarded-for` supplies the source; local development uses one local source. Other production hosts fail closed until a trustworthy source adapter is added.

The five-attempt rule protects this website route. Supabase's public Auth endpoint remains reachable with the public key and has its own provider rate limits; this package does not claim a provider-wide five-attempt account lock. Shared accounts also cannot attribute actions to individual staff. These are explicit implementation limits.

Only a narrow private definer helper can lock/read the confirmed Auth user. Browser roles cannot execute it or any onboarding/cooldown RPC. Public RPCs run as the caller, with execute grants restricted to service_role. Private tables have RLS enabled with no browser grants.

## Rollback

Remove application usage before running the local/staging rollback file. It removes package functions and private counters/retry records; it leaves created accounts, restaurants, memberships and audit records intact. The release excludes the separate D2-B editor and B0 Admin paths.
